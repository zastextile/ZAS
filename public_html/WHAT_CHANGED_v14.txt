THE BUG YOU FOUND IN v13 — TYPING DID NOT FILTER
------------------------------------------------

You reported: the list opens, but typing does nothing until you press
the down arrow. That is exactly right, and here is the cause.

v13's LOV listened for three events:

    focusin     open the list
    keydown     arrows, Enter, Esc
    focusout    close it

There was NO 'input' listener. Typing changed the box's value and
nothing redrew. Pressing ArrowDown ran the keydown handler, which calls
lovDraw(), and lovDraw() reads the box — so the filter appeared to work
only after an arrow key.

Fixed in the shared engine:

    root.addEventListener('input', function (e) {
      if (!S.open || e.target !== S.f) return;
      S.idx = 0;        // a new query starts at the top of the list
      load();           // ask the screen for rows again
    });

WHY MY TESTS MISSED IT, WHICH MATTERS MORE THAN THE BUG

Every test I had ran the filtering FUNCTIONS directly — give it "thred",
check it returns THREAD. Not one of them ever fired an event. So the
filter was provably correct and provably unreachable at the same time.

There is now lov_events_test.js, which drives the LOV the way a keyboard
does: focus the cell, type, arrow, Enter, Esc, Tab — and asserts the list
reacted to each. It fails against v13 and passes against v14. That class
of bug cannot get past it again.

CONSUMPTION — THE CASCADE YOU ASKED FOR
---------------------------------------

Your rule: choose one field and the next shows only what relates to it.
On Consumption the chain is not party → contract → item, it is:

    Order (proforma)
        -> only the products that order actually makes, and only the
           lines the floor has already started
    Product
        -> only the materials that product's COSTING uses
    Material
        -> only the lots of it really on the floor, oldest first

The data for this was already here. What was missing was showing it: the
material box was a dropdown of every item in the business with the wrong
ones merely hidden, no balance anywhere, and nothing to say why an item
was missing. It is now the same LOV, and every row carries:

    Code · Description · In costing · On floor · UOM · Rate

"In costing" says yes or no. Materials in the costing rank first; ones
outside it are hidden until you tick "Show every material", which then
marks them rather than pretending they belong. That tick already existed
and still works — it is now honest about what it is doing.

The rate is derived from the ledger (value ÷ quantity at that location),
not from the item master's planning rate. The final number still comes
from the FIFO allocation lot by lot, which is more accurate than any
single figure — the LOV rate is what you see before you commit.

WHAT I DID NOT CHANGE: the lot picker on Consumption. It is a full
screen with a ledger view, multi-lot selection and FIFO override, which
is more than an LOV can be. Making it a dropdown would have been a
downgrade. It stays as it is.


STORE ISSUE / RETURN
--------------------

Same LOV. A store movement never creates or destroys stock, it only
changes where stock is — so the only question is "what is at the place
it is leaving". The list is the FROM location's stock, with balances.
Change the From box and the list changes with it.
