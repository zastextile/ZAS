WHY YOUR SCREEN LOOKED BROKEN — I FOUND IT, AND IT WAS MY FAULT
===============================================================

THE STYLESHEET WAS NEVER CACHE-BUSTED.

includes/layout.php linked it like this:

    <link rel="stylesheet" href="assets/css/app.css">

No version. So a browser that had already downloaded app.css KEPT SERVING THE
OLD ONE. You uploaded the new app.css to the server, but your browser never
asked for it.

In v25 I rebuilt the Product Master form using NEW classes — .zform, .zsec,
.zrow, .zlab — that only exist in the NEW app.css. Your browser had the new
MARKUP (from product_master.php, which is not cached) and the OLD STYLES. The
result is a form with no styling at all: plain stacked boxes, no spacing, no
layout. "Completely view disturbed" is exactly right, and it is exactly what
that combination produces.

This was my mistake in the plain sense: I shipped markup that depends on new
CSS without making sure the new CSS could actually arrive.

FIXED:
    <link rel="stylesheet" href="assets/css/app.css?v=26">

The two JavaScript files carry ?v=26 as well, so all three refresh together.
A comment in layout.php tells whoever changes app.css next to raise that
number, and a test fails if it is ever linked bare again.

IF YOU STILL SEE A BROKEN SCREEN AFTER UPLOADING THIS, it is the browser
holding the old file harder than usual. Press CTRL+F5 (or CMD+SHIFT+R) once
on that page. After this upload you should never need to do that again.

ALSO IN THIS ZIP, from v26: the rail fix. I had made the left rail appear only
while editing, which removed your Parts & Operations link AND re-flowed the
list page, because .pm-layout is a flex row and I deleted its 200px first
column. The rail always renders again. A test now fails if it is ever made
conditional.

Both of your complaints about Product Master were caused by me, in the same
release, and neither was anything you did.


WHY THE EXPORT DID NOT SHOW YOUR LATEST PRODUCTS
=================================================

THE SAME KIND OF FAULT: A CACHED DOWNLOAD.

pob_send_csv() sent the file with no cache headers at all:

    Content-Type: text/csv
    Content-Disposition: attachment; filename="production_operations.csv"

The download URL never changes — it is always ?download=operations. With no
cache headers a browser is entitled to hand you back the file it downloaded
last time instead of asking the server again. So you pressed Export, and got
the export from BEFORE you added those products.

THE QUERY WAS NEVER WRONG. I checked it: it reads live from the database every
time, joins products, and includes every active product with no operations at
all as a blank starter row. It was simply never being asked.

FIXED, three ways:

  1. NO-CACHE HEADERS on every export:
         Cache-Control: no-store, no-cache, must-revalidate, max-age=0
         Pragma: no-cache
         Expires: 0
     (all three, because the older two are what some proxies still obey)

  2. A STAMPED FILENAME. Every download now carries the date and time:
         production_operations_2026-09-11_2140.csv
     Two exports can never be confused in your Downloads folder again, and
     the newest is obvious by name.

  3. A LIVE COUNT ON THE PAGE, above the export buttons:

         Right now: 47 active products · 312 active operations ·
                    9 products with no operations yet.

     Counted as the page loads, straight from the database. Press Export and
     compare. IF THE FILE DISAGREES WITH THAT LINE, IT IS AN OLD DOWNLOAD —
     reload the page and press again. You now have a way to tell, instead of
     wondering.

ONE THING TO KNOW, stated on the page too: ONLY ACTIVE PRODUCTS ARE EXPORTED.
A product switched off in Product Master will not appear in the file. That is
deliberate and unchanged — but it was never written down, so if a product is
missing, check its Active tick first.
