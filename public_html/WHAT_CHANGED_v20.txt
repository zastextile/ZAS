1. THE PART LIBRARY — YOUR IDEA, BUILT
--------------------------------------
Menu: Product Costing > Part Library.

Define Bed Sheet ONCE — its operations and their rates. Then on any master
product, "Import a part from the library" and its operations arrive already
priced.

IMPORTING COPIES. It writes ordinary production_operations rows, exactly
what you would have typed. Production, wages, the CSVs, the entry screen —
none of them know a library exists. If the library were deleted tomorrow
every product would keep working unchanged.

  · A part already on the product is SKIPPED, never duplicated. Importing
    twice is harmless.
  · The operations land at "All sizes". Scope one to a single size later,
    in the grid, if it genuinely costs different there.
  · Every size gets a quantity of 1, so the part appears in the Size
    Variant cards straight away instead of waiting to be noticed. A count
    you have already set is NOT reset by a re-import.

NO QUANTITY LIVES IN THE LIBRARY. Not even a suggested one. How many go in
a set is per product AND per size — Pillow Cover is 2 in a Single and 4 in
a King, same part, same rate, different count. So an imported part lands at
1 and the box beside its name is where it changes.

WHEN A STANDARD RATE MOVES: "Check what would change" lists every product
that would change, old -> new. A row whose rate you edited ON THE PRODUCT
is UNTICKED by default and flagged "you edited this" — that is your number,
and a careless update would quietly undo it. Nothing moves until you press
Apply. A row you do apply becomes the new baseline, so it is not reported
at you again.

Deleting a library part does NOT touch the products that imported it. They
hold copies. The link is cleared so a later re-apply cannot point at
something that no longer exists.


2. SIZE VARIANTS — CARDS, NOT A MATRIX
--------------------------------------
Still ONE page. Everything is on product_master.php?edit=N, and the side
nav jumps between sections on it — Basic Information, Packing Information,
Parts & Operations, Size Variants. Nothing opens a second screen. (Those
last two nav entries used to say "Production Operations" and "Components",
which no longer matched the headings they jump to; they do now.)

The old "How Many Per Set" grid (parts across, sizes down) is gone.

Each size is now its own CARD, the same shape as a costing version:

    Sheetset · SIZE VARIANT · [Single]    [⎘ Duplicate Variant] [Delete]
      [1]  bed sheet      priced for all sizes    1 × 8.00 = 8.00
      [1]  pillow cover   priced for all sizes    1 × 3.50 = 3.50
                                    workmanship / set   PKR 13.50

THE QUANTITY IS ONE BOX, NEXT TO THE PART NAME. Blank still means 1 — that
is what the database has always meant, so the screen now says the same.

⎘ DUPLICATE VARIANT copies the whole thing: every part, every count, and
any rate priced for that size alone. It lands named "Single copy" — rename
it King, change the one count that differs, done. This is Duplicate Costing
one level down; nobody has to learn a second idea.

Deleting a variant removes its counts and its size-scoped rates. It REFUSES
if a costing version applies to that size, and says how many — deleting it
would leave the costing pointing at nothing.

Renaming a variant saves with the same button as the quantities. One Save,
not two. The size id never changes, so every rate and count follows the
rename by itself. Ctrl+S works inside a variant card, the same way it works
inside the operations grid — each is guarded by where the cursor is, so the
two never fight over the keystroke.

After Duplicate Variant the page comes back with the cursor already in the
new name box, scrolled to it. Rename, change the count, Ctrl+S.

The parts inside a card are one column, so Enter walks down them, Ctrl+D
fills down, and a column of counts copied out of Excel pastes straight in.


2b. CHANGING A SIZE AFTER YOU IMPORT — ALL THREE WORK
-----------------------------------------------------
  ADD A SIZE at any time. "+ Add" below the cards. The new variant lists
  every part the product already has, each at 1, because a missing quantity
  row has always meant 1. Set the ones that differ and Save. Nothing needs
  re-importing.

  CHANGE A COUNT per size — the box beside the part name, in that card
  only. The other sizes do not move.

  PRICE ONE SIZE DIFFERENTLY — in Parts & Operations add a row for the same
  part and operation, and set "Applies to" to that size. The card then
  marks it "priced for this size".

    !! A SIZE-SCOPED RATE OVERRIDES. IT DOES NOT ADD. !!

  Per operation, a rate priced for that exact size WINS; otherwise that
  operation's "All sizes" rate is used. So "sew" at 5 for all sizes plus
  "sew" at 7 for King costs 7 in King — not 12.

  That is production's own rule (production_operation_rate_for_size(), in
  includes/production.php) and it has always been the rule. The new card
  was ADDING them, which would have shown you a cost the floor never
  charges. Fixed, and now checked by a test that runs both resolvers on the
  same data and fails if they ever disagree.

  Two consequences worth knowing:
    · A NEW operation priced only for King (say "embroidery") has nothing
      to override, so it adds — for King only. Single contributes 0 for it.
    · To make King's "sew" cost more, price "sew" for King. Do not add a
      second differently-named row, or you will be charged for both.


2c. THE BLANK PART ON THE DISPATCH ROW — WHAT IT ACTUALLY DOES
--------------------------------------------------------------
Keep it blank. It is not cosmetic; it is a switch, and the code that reads
it is production_api.php lines 75-83:

    $comp = trim(component_name of the operation);
    if ($comp !== '') {                       <-- a PART is named
        $ordered = order qty x qty_per_set;         counted in PIECES
        progress = that ONE part's progress
    } else {                                  <-- BLANK
        $ordered = order qty;                       counted in SETS
        progress = the whole item's progress
    }

So writing a part name on your packing row changes three things at once:

  1. The limit stops being 100 sets and becomes 100 x that part's per-set
     count — 200 for a part that goes in twice.
  2. The entry screen starts asking your packer for PIECES of that part
     instead of SETS packed.
  3. The wage changes with it: the rate is per unit entered, so a PKR 2
     packing rate on 100 sets is 200, but on 200 pieces it is 400.

NEW RULE — DISPATCH MAY NOT MIX. Having BOTH a blank Dispatch row and a
Dispatch row that names a Part is now refused, on screen and again on the
server, naming the offending rows. The reason: the blank row reads the
item's whole Dispatch progress, which SUMS every part. Book 40 on a named
Dispatch row and the packing row's remaining silently moves by 40 — pieces
added into a set total.

Either leave every Dispatch row blank (one packing step, counted in sets —
what you want), or name a Part on every one (each part dispatched
separately, counted in pieces). Not both.

SEPARATELY, AND STILL NOT FIXED: the packing row's ceiling is
stitched-minus-dispatched where "stitched" sums every part. On 100 sets of
a 2-part product, fully stitched, packing offers 200 as remaining instead
of 100. That is the deferred item in section 8 — packing's derived ceiling,
MIN over parts of (finished / per-set). It is pre-existing, not new here,
and it needs a schema change. Say when and I will demo it.


3. WHY IT IS TWO SECTIONS AND NOT ONE
-------------------------------------
Worth reading once, because it is the decision behind the layout.

An operation is stored PER PRODUCT — production_operations.product_size_id
is NULL for "all sizes", which is what nearly every row you have is. A
quantity is stored PER SIZE.

So rates cannot sit inside a size card. If "sew" appeared under Single and
you changed it there, you would be changing King too and the card would be
lying to you. The alternative is duplicating every rate per size, and a
five-part set in nine sizes becomes 405 rows to maintain instead of 45.

Hence: Parts & Operations priced once at the top. Size Variants below,
where only the counts differ. The cost beside each part respects "Applies
to" — a rate scoped to another size does not leak into this card, and a
deactivated operation stops counting.


4. A SIZE BUG IN PRODUCT COSTING, FIXED
---------------------------------------
Found while checking your question about sizes being in two places.

They are not: product_sizes is ONE table, and both screens write the same
rows. But Costing's save sent the real size id (buildPayload, line 874) and
then THREW IT AWAY — it matched sizes by LABEL instead.

So: rename a size in Product Master, then save a Costing tab that was
already open with the old name, the label is not found, and a SECOND size
row is inserted. "King" and "King Size" on one product, each with its own
quantities. That was the only route by which your one list could become
two.

THE FIX: look up by id first; the label is a fallback only for a size the
browser has never had an id for. A recognised id also carries the rename
across, so the two screens converge instead of drifting apart.

No schema change.


5. WHERE SIZES LIVE — THE RULE
------------------------------
PRODUCT MASTER OWNS THE LIST. Costing and Production both consume it.

  · Sizes outlive costings. You re-cost every season; King stays King.
  · Production depends on them — product_component_qty.product_size_id and
    production_operations.product_size_id both point at them. The factory
    cannot be waiting for someone to open a costing screen.
  · Product Master already behaves like the owner: duplicating a product
    copies its sizes and remaps every reference; deleting one deletes them.
  · Costing already treats them as a selection — "Applies to sizes" ticks
    from a list it did not create.

Costing keeps its size box. It is now a shortcut into the same list rather
than a second definition of it.


6. SCHEMA — ALL ADDITIVE, ALL SELF-HEALING
------------------------------------------
Two new tables:
    part_library                  id, part_name (unique), notes, is_active
    part_library_operations       part_id, operation_name, stage, rate

Two new nullable columns on production_operations:
    lib_part_id       which library part this row came from (NULL = typed)
    lib_base_rate     the rate when it was imported or last re-applied

A row with lib_part_id NULL behaves exactly as it does today. Every
existing row is one of those. Nothing is migrated, nothing is rewritten.
