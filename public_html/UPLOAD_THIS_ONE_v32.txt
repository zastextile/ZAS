WHAT IS NEW  —  the screens you drew
================================================================

1. PART LIBRARY  (part_library.php)
-----------------------------------
Three boxes at the top:  Part ID · Part Name · Style (optional)

  · Part ID is shown, never typed. It is what the CSV and every product
    import use to find the part again.
  · Style offers the styles already in the library, and still takes a
    new one you type.

Then one grid:  #  ·  Stage  ·  Operation  ·  Rate / pc  ·  Action

  · Line 1 is Cutting, the word already written in, and the cursor
    starts ON ITS RATE. The only thing you have to say about cutting
    is what it costs.
  · Line 2 onward is Stitching, cursor on the OPERATION.
  · Enter, Tab and the right arrow go forward. Up and down move
    between lines. Going forward off the last rate makes a new line.
  · THE KEYBOARD NEVER ENTERS THE STAGE COLUMN. The Stage box is
    mouse-only on purpose, for the rare second cutting — and that one
    must be given a name, because two lines both called "Cutting"
    would pay for the same work twice.
  · Leave an operation name blank and it takes its stage as the name.
    A line blank in BOTH boxes is nothing at all.

NO FINISHING BOX. NO RATE AT THE TOP.
"Finish" is an ordinary stitching operation you type, paid per piece
like Singer or Overlock.

PACKING IS NOT HERE. A part is not packed — a SET is, and how many
parts make a set lives on the product with its sizes. Dispatch is gone
from the stage list.

Per part: Save/Update · Edit · Copy · Delete, each with its ID visible.
Parts delete freely. A product that imported one keeps its own copy, so
deleting a library part never changes anything on the floor.

CSV out and back in, one line per operation — which is also exactly
what Excel puts on the clipboard, so you can paste a block straight
into the grid. The Part ID column makes a rename survive the round
trip. Nothing is written unless every part in the file passes: one bad
line leaves the library exactly as it was.


2. MASTER PRODUCTS — NEVER DELETED  (product_master.php)
--------------------------------------------------------
A new "Used In" column, and the Delete button is greyed out whenever
anything uses the product.

  · Used in any production entry, order, invoice, shipment or costing
    → Delete is OFF. Deactivate instead: it leaves every list, and
    every record that points at it stays intact.
  · Once nothing references it at all → Delete turns back on. That one
    is a typo being cleaned up, not a product.
  · A check that CANNOT RUN counts as used. A count that fails never
    reads as "safe to delete".

The server enforces this too, not just the greyed-out button. If you
post a delete for a product that is in use, it deactivates it and tells
you exactly what was in the way.

THIS FIXES A REAL HOLE. The old Delete had no check of any kind: it
removed the product and its sizes, and left its operations, its
production history and its cost sheets pointing at nothing.

Importing a part now asks WHICH SIZES — "All", or pick the ones you
want. A size you leave out simply does not use that part, which is how
a Single takes one pillow and a Double takes two. It lands at 1, and
re-importing never resets a number you already set.


3. ORDER RATE AMENDMENTS  (production_order_rates.php — NEW)
------------------------------------------------------------
Production → Order Rate Amendments.

When one buyer's order is worth more for one operation — a tighter hem,
a quality parameter written into the contract — amend it THERE.

  · LOCKED BY DEFAULT. Press Unlock on a line, type the rate and a
    reason, and it saves and locks again.
  · THE REASON IS REQUIRED. An unexplained rate change six months later
    is indistinguishable from a mistake.
  · THIS ORDER ONLY. The master product keeps its rate, the library
    keeps its rate, every other order keeps paying the standard.
  · WORK ALREADY BOOKED IS NEVER RE-PRICED. Every production entry
    carries the rate it was booked at, so an amendment changes what is
    paid from now on and can never quietly restate a wage somebody has
    already earned. The screen shows that figure next to each line.
  · Withdraw puts a line back on the standard rate, and the withdrawal
    is recorded too.

Only an admin can move a rate. A colleague can read the screen — which
is the point of an audit trail.


4. RATE CHANGE HISTORY
----------------------
Every rate change is now recorded, from all three places a rate lives:

    library   the Part Library definition
    product   one operation on one master product
    order     an amendment on one production order

From → to, who, when, and why. Shown at the bottom of the Part Library
and on the order rate screen. Never edited, never deleted.

Both the Part Library and the Product Master operations grid now have a
"why the rate changed" box. It is only needed when you actually move a
rate; leave it empty the rest of the time.


================================================================
TWO BUGS FOUND AND FIXED ALONG THE WAY
================================================================

1. OVER-CUTTING WAS ALWAYS REFUSED.
   includes/production.php read the over-cut reason out of a variable
   that does not exist in that part of the code ($r instead of $e). The
   reason was therefore ALWAYS empty, so the "cutting above the plan is
   allowed if you give a reason" path could never be reached. Every
   over-cut was refused — with a message telling you to do the exact
   thing the code then ignored. Now it reads the right variable and
   works as it was always described.

2. THE NEW PART LIBRARY GRID WOULD NOT HAVE LOADED AT ALL.
   My own bug, caught by the tests before it reached you: a line
   registered a handler for a function defined further down the file,
   which throws in the browser and would have killed the whole keyboard
   block. Fixed, and the test now presses real keys against the real
   code so it cannot come back silently.
